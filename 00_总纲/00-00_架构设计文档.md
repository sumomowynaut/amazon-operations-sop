## 0. 设计总纲

本知识库不是 Amazon 介绍文章，而是一套可执行、可验证、可维护的运营操作系统，遵循 5 条硬性原则：

1. **闭环原则**：理论 → 判断 → 决策 → 操作 → 数据 → 复盘 → 优化，每个模块必须闭环。
2. **真实性原则**：官方规则与运营经验严格分离；标注证据等级、资料来源、访问/更新时间；无法确认内容标注「待验证」；资料冲突必须并列说明。
3. **可执行原则**：SOP 不出现「进行优化」「分析数据」这类不可执行描述，必须写成「进入 Seller Central → XXX → 检查 XXX」。
4. **统一结构原则**：每个 SOP 强制采用统一 17 节结构（见下）。
5. **版本原则**：v1.0 之后建立 v1.1 / v1.2 的固定更新机制（季度政策校验 + 月度数据校准 + 触发式更新）。

### SOP 统一结构（17 节，每份强制遵循）

1 模块目的 / 2 适用场景 / 3 核心概念 / 4 核心指标 / 5 决策树 / 6 标准操作流程 / 7 操作前检查 / 8 操作后检查 / 9 成功标准 / 10 失败处理 / 11 常见错误 / 12 风险 / 13 实战案例 / 14 Checklist / 15 数据记录模板 / 16 复盘方法 / 17 关联模块。

### 证据等级（全文强制标注）

| 等级 | 定义 | 使用要求 |
|---|---|---|
| A | Amazon 官方规则（政策/条款/费率表） | 必须附官方链接与访问日期，加「需定期验证」 |
| B | Amazon 官方资料/培训（Seller University、Ads 官方文档、帮助页） | 附来源与访问日期 |
| C | 行业公开资料（第三方工具白皮书、行业报告） | 注明发布方与时间 |
| D | 成熟运营者经验（团队内部验证过的经验） | 标注「经验值，非硬性标准」 |
| E | AI 推理/假设 | 仅作待验证思路，禁止作为决策依据 |

严禁把 D/E 写成 A。

## 1. 完整知识体系（五层架构）

```
L4 管理层        运营节奏与复盘 │ 团队与培训
L3 横向支撑层    数据与诊断     │ 风控与异常
L2 业务主链路    市场→选品→产品→供应链→Listing→广告→转化→库存→利润
L1 合规边界层    平台规则与账户（一切操作的红线）
L0 底座层        证据等级·术语表·数据来源·维护规范
```

## 3. 模块依赖关系

### 3.1 依赖总表

| 模块 | 强依赖（必须先有） | 弱依赖（建议先有） | 被谁依赖 |
|---|---|---|---|
| 00 总纲 | 无 | 无 | 全部模块 |
| 01 平台规则 | 00 | 无 | 全部模块（红线约束） |
| 02 选品 | 00, 01 | 08-01 数据指标 | 03 产品、09 利润 |
| 03 产品/供应链 | 00, 01, 02 | 09 利润 | 04 Listing、07 库存 |
| 04 Listing | 00, 01, 02-03 关键词 | 03 产品定义 | 05 广告、06 转化 |
| 05 广告 | 00, 01, 04, 09-01 利润口径 | 08 数据 | 06 转化、08 诊断、09 利润 |
| 06 转化/客户体验 | 00, 01, 04 | 05 广告 | 08 诊断、09 利润 |
| 07 库存 | 00, 01, 03 供应链周期, 08 销量预测 | 09 利润 | 09 利润、10 异常 |
| 08 数据与诊断 | 00, 01, 04, 05, 06, 07, 09 的指标定义 | 无 | 全部模块（横向） |
| 09 利润 | 00, 01, 05, 07, 06 | 02 | 02 选品测算、08 诊断 |
| 10 风控与异常 | 00, 01, 08 诊断树 | 全部业务模块 | 全部模块（横向） |
| 11 运营节奏 | 00, 08 | 01-10 | 12 培训 |
| 12 团队培训 | 00, 11 | 01-10 | 无（消费全部） |

### 3.2 关键结论

1. **00 与 01 是地基**：所有模块都必须先定义证据等级、合规边界，否则后续内容会「经验污染规则」。
2. **08 是横向主轴**：诊断树依赖各业务模块的指标定义，同时又反向被所有异常处理调用；因此 08-01（数据指标体系）必须在业务模块之前先定「指标口径」。
3. **09-01（利润口径）必须先于 02 和 05**：否则选品测算与广告 ACOS/TACOS 判断会失去锚点。
4. **05 广告是交叉密度最高的模块**：同时依赖 Listing（内容）、利润口径（目标）、数据（诊断），又输出给转化、利润、异常三处。

## 4. 必须优先研究的模块

优先级排序原则：资金/合规风险 × 前置依赖数量 × 使用频率。

| 优先级 | 模块 | 理由 |
|---|---|---|
| P0（第一批） | 00 总纲、01 平台规则、08-01 数据指标体系、09-01 利润口径 | 四者是全部模块的「语言与边界」，不定清楚后面全部返工 |
| P1（第二批） | 02 选品与利润测算、05 广告（SP 优先）、07-02/07-03 库存补货与断货、04 Listing/SEO | 主链路最高频、资金影响最大；用户明确要求广告重点展开 |
| P2（第三批） | 10 异常处理、11 运营日历、03 供应链、06 转化/VOC | 异常手册依赖 P1 的诊断树；日历是日常落地入口 |
| P3（最后） | 12 团队培训、08-07 周月报、08-06 利润诊断树 | 消费型模块，等核心内容稳定后再写，避免反复改 |

## 5. 最容易出错的模块

| 排名 | 模块 | 高频错误 | 后果 |
|---|---|---|---|
| 1 | 05 广告 | 把相关性当因果；只看 ACOS 不看 TACOS；否定过度；频繁调价；忽视归因窗口 | 预算烧完、自然排名下滑 |
| 2 | 09 利润 | 漏算退货/仓储/Coupon/广告费；口径混用（毛利 vs 净利）；用售价做锚点 | 账面赚钱、实际亏损 |
| 3 | 07 库存 | 忽视 Lead Time 波动；安全库存拍脑袋；只看到仓库存不看在途 | 断货损失排名 / 积压仓储费 |
| 4 | 01 平台规则 | 用过时政策；把 D 级经验写成 A 级规则；不标注「需定期验证」 | 违规、账户风险 |
| 5 | 08 诊断 | 单点归因；销售下降直接怪广告；忽略多变量交互 | 错误操作放大损失 |
| 6 | 06 Review/VOC | 触碰违规索评/改评；误用官方沟通边界 | 账户处罚 |
| 7 | 02-03 关键词 | 混淆「搜索量」与「相关性」；忽视长尾与购买意图 | 选品与广告双输 |

## 6. 必须引用 Amazon 官方资料的模块

以下模块核心事实必须来自 A/B 级官方资料，且附链接 + 访问日期 + 「需定期验证」：

| 模块 | 必须官方化的内容 |
|---|---|
| 01-02 账户健康 | 绩效指标（ODR、VTR、迟发率等）定义与阈值 |
| 01-03 品牌注册 | Brand Registry 资格、品牌保护工具 |
| 01-04 合规审核 | 类目审批、受限商品、危险品政策 |
| 01-05 知识产权 | 侵权投诉与申诉流程 |
| 05-01~05-04 广告 | SP/SB/SD 的资格、竞价机制、广告位、归因 |
| 05-13 Deal | LD/7DD/DOTD 的资格与费用 |
| 06-01 BuyBox | Buy Box 计算机制（官方解释范围） |
| 06-02 Review | 评论政策、请求评论按钮规则 |
| 07-04 IPI/仓储费 | IPI 阈值、月度/长期仓储费费率 |
| 09-02 费用 | 佣金比例、FBA 配送费、仓储费（费率表） |

注：官方未公开的「内部机制」（如 A9/A10 权重、Buy Box 精确公式）必须标注「官方未公开，属行业经验/推测」，不得编造固定权重。

## 10. 项目实施路线

### 阶段划分（对应你定义的 8 个阶段）

| 阶段 | 内容 | 产出 | 完成标准 |
|---|---|---|---|
| 0 初始化 | 建目录、命名规范、证据等级模板、17 节模板、维护机制 | 规范文件 | 模板可被任何作者直接套用 |

### 更新机制（v1.1+）

- **季度政策校验**：所有 A/B 级内容（费率、资格、阈值）逐项复核并更新「访问日期」。
- **月度数据校准**：经验值（D 级）用真实数据回测，偏离超阈值则修正。
- **触发式更新**：平台政策变更、重大异常、产品上新时即时更新对应 SOP。
- **版本纪律**：每次改动记录 changelog，标注改动证据等级，避免「静默改规则」。

### 建议节奏（单运营 + AI 辅助）

- 阶段 0-2：1-2 天
- 阶段 3：3-5 天（官方资料核实最耗时）
- 阶段 4：10-15 天（86 份，日均 6-8 份）
- 阶段 5-8：5-7 天
- 合计：约 4-6 周形成 v1.0（视资料核实难度浮动）
